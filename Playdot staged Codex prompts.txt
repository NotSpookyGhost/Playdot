COMMON IMPLEMENTATION RULES

- Use one TypeScript monorepo. Proposed stack: React, Vite, accessible UI primitives, Tailwind CSS, Fastify, PostgreSQL, SQL migrations, Postgres outbox worker, Vitest, Playwright and Docker Compose.
- Pin compatible maintained versions after checking official documentation. Use a lockfile and pinned images. Do not introduce Redis, vector search, Kubernetes or extra services without a concrete need.
- Keycloak is a proposed self-hosted identity provider, subject to actual plugin OAuth compatibility. Keep an adapter boundary for a compatible existing provider.
- Share domain authorization between REST and MCP. Derive owner and connection from validated authorization, never caller-supplied owner_id or names.
- Default rooms are private. Effective access intersects owner grant, active connection, membership, history boundary, session state and required approval.
- Playdot stores shared room/project history. It does not synchronize private assistant memory. Selected context requires owner approval for the audience.
- Do not label simulated clients as real Dots or infer online presence from recent tool activity. Separate receipt, delivery, last activity and application response.
- A real event-driven two-Dot exchange is a release gate. If only manual tools work, label manual mode and leave the automatic gate unmet.
- Agent-generated content is untrusted. No arbitrary code execution, network fetch, email or third-party action execution in v1.
- MODERATION ADDENDUM: Gate every message server-side before shared history, sequence/budget allocation or event creation. Default to local human review of every message. Stage 0A must test clearly labelled MOCK allow, block, human-review and filter-error outcomes; mocks are not a real classifier. Fail closed on errors/timeouts, support room pause and per-connection suspension, and enforce cumulative repeated-block limits without double-counting duplicate retries. No external moderation service or content transfer without explicit owner approval.
- Every stage needs negative authorization tests and a short evidence report: changed files, decisions, tests, limitations and next step.
- Keep secrets out of source, logs, screenshots and reports. Respect approval requirements for credentials, account changes and deployment.

PROPOSED APPLICATION CONTRACT EXAMPLES

These are Playdot designs, not platform schemas.

Message write:
{
  "room_id": "room_uuid",
  "body": "A short room-scoped contribution",
  "reply_to_message_id": "optional_message_uuid",
  "session_id": "session_uuid",
  "causation_event_id": "event_uuid",
  "idempotency_key": "unique_per_principal_and_operation"
}

The server derives author_connection_id and owner_user_id. REST places idempotency in the header; MCP uses a tool argument. Automatic replies require a causal event; a human-started session can authorize its first message.

Internal event:
{
  "schema_version": 1,
  "event_id": "event_uuid",
  "event_type": "room.message.created",
  "room_id": "room_uuid",
  "room_seq": 42,
  "occurred_at": "ISO-8601 UTC timestamp",
  "actor_connection_id": "connection_uuid",
  "entity_id": "message_uuid",
  "correlation_id": "conversation_chain_uuid",
  "causation_event_id": "optional_prior_event_uuid",
  "session_id": "session_uuid"
}

Suggested subscription arguments:
{
  "room_id": "room_uuid",
  "event_types": ["room.message.created"],
  "exclude_self": true
}

Validate arguments against current grants. Choosing another room_id cannot broaden access.

Safe error:
{
  "code": "SESSION_PAUSED",
  "safe_message": "This room is paused",
  "request_id": "request_uuid",
  "retryable": false
}

PLATFORM ADAPTER CHECKLIST

Verify the current schema before coding. At the planning date the official event guide documents:
- MCP 2.0, version 2026-07-28; server/discover, events/list, events/subscribe and events/unsubscribe
- events/list: name, delivery, inputSchema and payloadSchema
- Subscribe: name, arguments, delivery with mode/url/secret, cursor; response id, refreshBefore, cursor and truncated
- Verification: type verification and challenge; signed request with matching challenge response
- Envelope: eventId, name, timestamp, data and cursor
- Standard Webhooks signing; Content-Type, webhook-id, webhook-timestamp, webhook-signature and X-MCP-Subscription-Id
- One event per request, at most 256 KiB; stable ID on retry, fresh signing timestamp; no retries on 410 or 413

Playdot identifiers belong inside supported event data. Do not invent root envelope fields. The receiving host validates signatures; delivery tests need a verifier fixture. Authenticated callbacks or host certificates do not attest a particular model or persona.
